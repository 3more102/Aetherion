# M18 — Aetherion Mobile: INT4 export + on-device benchmark

## Scope and status

This extension of M17 adds **weight-only 4-bit quantization** of eligible
MatMul ONNX operators using ONNX Runtime's MatMulNBits, plus a local
browser timing report. Activations remain floating-point; embeddings and
other unsupported operators are **not** automatically 4-bit. The actual
file-size ratio and numerical drift must be read from the generated
manifest, not assumed from the bit width.

There is **no released trained assistant checkpoint**, no independent
semantic-quality assessment, and no confirmed all-phones support.
Phone hardware benchmarks must be collected on real devices.

## Requirements

On a development PC with Python 3.11, PyTorch and tokenizers installed:

    python -m pip install -r requirements.txt
    python -m pip install onnx==1.23.2 onnxruntime==1.32.0 onnx_ir

The MatMulNBitsQuantizer class is the API for ONNX Runtime 1.29+.
Official docs may still show the older MatMul4BitsQuantizer API.
For the mobile frontend, run npm install and npm run stage-runtime
from mobile/ as described in [M17](M17_MOBILE.md).

## Convert a trusted byte-level Aetherion-Micro checkpoint

    python export_mobile.py --checkpoint checkpoints/my-micro.pt \
      --window 32 --output-dir mobile/artifacts/fp32

    python quantize_mobile.py \
      --model mobile/artifacts/fp32/model.onnx \
      --manifest mobile/artifacts/fp32/manifest.json \
      --output-dir mobile/artifacts/int4 \
      --block-size 32

Expected outputs in mobile/artifacts/int4/:

- model.int4.onnx
- manifest.int4.json

The conversion fails if the source model does not match the manifest
SHA-256, if there are zero quantized MatMul nodes, or if its ONNX graph
cannot load in the desktop CPU ONNX Runtime used for conversion.

The manifest records: original/INT4 hashes and file sizes, number of
converted MatMul nodes, exact block size, and synthetic logit comparison
(error values and top-token agreement). **This is not language quality
validation or proof of inference on a mobile device**.

## Run on the phone

1. Serve mobile/ over HTTPS with all staged vendor/ files.
2. Open the app from a supported Android or iOS browser.
3. Select model.int4.onnx and manifest.int4.json transferred to the phone.
4. Load the model and run a short prompt.
5. Tap **Benchmark (16 steps)** to record local timing metrics.

The benchmark report displays measured step latency, warmup count,
sample count, tokens/s, model SHA, model format, browser-reported
RAM (if supported), and user agent. The report stays on the phone unless
the user chooses to copy/share it. Generated "tokens" are UTF-8 bytes,
not semantic language tokens, so comparisons to tokens/s figures from
BPE-based commercial models are invalid.

## Limitations / next engineering gates

- M18 has no ONNX KV-cache graph; the M17 fixed-window computation is
  rerun for each generated byte. A cached decode path remains a separate
  milestone, requiring strict RoPE position and attention parity tests.
- Blockwise symmetric int4 may introduce unacceptable numerical drift.
  Evaluate a *trained* model on held-out tasks before distribution.
- MatMulNBits support and speed must be tested in real ONNX Runtime Web
  WASM sessions on target phones. The desktop ORT parity test alone is
  insufficient. Some phones may run *slower* after quantization.
- No production app binaries (APK/IPA), cloud sync, or remote inference API.
- A 5M-parameter bound from M17 remains; model quality is not implied.
- All file hashes are integrity checks, not authenticity signatures.
  Verify sources through trusted channels.
